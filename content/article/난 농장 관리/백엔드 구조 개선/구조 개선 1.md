농장 관리 시스템의 베타 버전을 만들 때는 필요한 기능을 빠르게 구현하는 데 집중했다.

농장의 난 묶음과 위치를 관리하는 기능에서 시작해 작업, 입고, 판매, 경매와 정산 기능을 차례로 추가했다. 각 기능은 Farm, Work, Inbound, Sales와 같은 모듈로 나누었고, 하나의 애플리케이션 안에서 업무별 경계를 구분하는 모듈러 모놀리스 구조를 사용했다.

기능이 적을 때는 이 구분만으로도 충분해 보였다. 하지만 실제 운영을 시작하고 구조 변경 작업이 늘어나면서 문제가 드러났다.

분갈이와 폐기는 Work에서 실행하지만 난 묶음의 수량을 바꾼다. 입고가 완료되면 Inbound에서 새로운 난 묶음을 만든다. 판매를 예약하거나 출고하면 Sales에서 판매 가능 수량을 확인하고 예약 수량을 변경한다.

하나의 난 묶음이 여러 업무의 결과로 바뀌는데, 각 모듈이 상태를 바꾸는 방법까지 직접 알고 있었다.

## 변경할 때마다 함께 확인해야 하는 것들

예를 들어 새로운 작업 유형 하나를 추가하려면 작업의 입력값만 검증해서는 끝나지 않았다.

* 실제 수량을 어느 서비스에서 변경하는지
* 판매 예약 수량과 충돌하지 않는지
* 여러 난 묶음을 함께 수정할 때 어떤 순서로 잠그는지
* 작업 이력과 재고 변경 이력을 어떤 순서로 저장하는지
* 중간에 실패하면 전체 변경이 취소되는지
* 같은 요청이 다시 들어오면 두 번 적용되지 않는지

를 함께 확인해야 했다.

패키지는 업무별로 나뉘어 있었지만 코드의 경계도 분명하지 않았다. Work와 Sales가 Farm의 JPA Entity를 직접 참조했고, Analytics는 여러 모듈의 QueryDSL 타입과 데이터 구조를 알고 있었다.

문제는 특정 서비스의 코드가 길다는 데 있지 않았다. 기능을 변경했을 때 어떤 모듈까지 확인해야 하는지 예측하기 어렵다는 것이 더 큰 문제였다.

> [시각자료 제안] 개선 전 의존 관계를 실제 패키지 분석 결과로 표시한 그림. Farm, Work, Inbound, Sales, Analytics 사이의 직접 Entity·QueryDSL 의존을 화살표로 구분하면 문제 설명의 근거가 된다.

## 엔진 하나를 추가하는 것으로는 부족했다

처음에는 난 묶음의 변경을 처리하는 `Mutation Engine`을 만들면 대부분 해결될 것이라고 생각했다.

하지만 상태 변경만 한곳으로 모아도 Work가 Farm의 내부 Entity를 알고 Analytics가 각 모듈의 DB 구조를 직접 조회한다면 기존 결합은 그대로 남는다. 새로운 엔진 위에 예전 호출 구조가 한 겹 더 생길 뿐이었다.

따라서 상태 변경 엔진을 만드는 작업과 함께 모듈 사이의 의존도 정리하기로 했다. 기준은 다음과 같이 잡았다.

```text
새로운 기능을 추가할 때
기존 핵심 코드의 수정 범위를 줄인다.

각 업무 규칙의 소유권을 분명하게 한다.

경계를 나누기 위해
필요하지 않은 계층까지 추가하지 않는다.
```

이 기준은 이후 인터페이스를 추가할 때뿐 아니라 이미 만든 구조를 제거할 때도 사용했다.

## 왜 바꿀지는 업무 모듈이 결정한다

상태 변경을 한곳에 모을 때 가장 조심한 부분은 Mutation Engine이 모든 업무 규칙을 아는 거대한 서비스가 되지 않도록 하는 것이었다.

폐기 작업을 실행할 수 있는지는 Work의 규칙이다. 출고할 수 있는 주문인지와 예약을 취소할 수 있는지는 Sales가 판단해야 한다. 입고 완료 조건은 Inbound가 알고 있어야 한다.

반면 업무 모듈이 내린 결정을 실제 난 묶음에 반영하는 과정에는 공통된 규칙이 있었다.

* 변경할 행을 잠근다.
* 현재 상태와 revision을 확인한다.
* 보유 수량과 예약 수량의 관계를 검증한다.
* 변경 후 revision을 증가시킨다.
* 변경 전후 상태와 Mutation을 함께 저장한다.

따라서 업무 판단과 상태 변경 방법을 다음과 같이 분리했다.

```text
Work / Sales / Inbound
        │
        │  왜 변경하는가
        ▼
의도가 드러나는 Command
        │
        ▼
OrchidGroupMutationEngine
        │
        │  어떻게 일관되게 변경하는가
        ▼
OrchidGroup + Mutation Ledger
```

업무 모듈은 변경 이유와 필요한 값을 Command에 담는다. Mutation Engine은 Work나 Sales의 내부 모델을 알지 않고 난 묶음의 상태를 안전하게 바꾸는 일만 담당한다.

상태 변경을 중앙화하는 것과 비즈니스 로직을 중앙화하는 것은 다른 문제였다.

## 무엇이든 바꾸는 API를 만들지 않았다

초기에는 변경할 필드 목록을 받아 한 번에 처리하는 범용 API도 검토했다.

```text
mutationEngine.execute(groupChanges)
```

호출부에서는 편리하지만 Engine의 관점에서는 왜 값이 바뀌는지 알 수 없다. 시간이 지나면 수량, 위치, 상태와 예약 수량을 원하는 값으로 바꾸는 범용 수정 서비스가 될 가능성이 높았다.

대신 외부에 공개하는 변경 방법을 의도가 드러나는 Command로 제한했다.

```text
CreateOrchidGroup
MoveOrchidGroup
DiscardQuantity
TransformOrchidGroups
ReserveQuantity
ConsumeReservation
CorrectOrchidGroups
```

새로운 변경 방법이 필요하면 명시적인 Command를 추가해야 한다. 이 과정은 코드가 조금 늘더라도 난 묶음이 어떤 이유로 변경될 수 있는지를 시스템의 계약 안에 남긴다.

## Mutation은 별도 모듈로 분리하지 않았다

Mutation Engine을 독립 모듈로 만드는 방법도 생각했다. 그러나 Mutation은 그 자체로 독립된 업무가 아니라 `OrchidGroup`의 상태를 바꾸는 메커니즘이다.

Engine은 난 묶음의 현재 상태와 수량, 예약과 상태 전이 규칙을 알아야 한다. 반대로 Farm도 Mutation의 결과를 사용한다. 둘을 억지로 나누면 `Farm ↔ Mutation`처럼 양쪽이 서로를 참조하거나 그 사이에 전달 객체만 늘어날 가능성이 컸다.

그래서 Mutation Engine과 이력은 Farm 안에서 난 재고를 담당하는 영역에 두었다.

```text
farm
└─ orchid
   ├─ OrchidGroup
   ├─ Mutation Engine
   ├─ Mutation Ledger
   ├─ Reservation
   └─ 상태 전이 정책
```

나중에 별도 서비스로 분리할 필요가 생긴다면 Mutation만 떼어 내기보다 난 재고 전체를 하나의 경계로 분리하는 편이 자연스럽다고 판단했다.

## 현재 상태와 변경 이력의 역할을 나누었다

변경 이력이 중요해지면서 Event Sourcing도 검토했다. 하지만 현재 시스템은 모든 이벤트를 다시 실행해 현재 상태를 계산할 필요가 없었다.

농장 현황과 작업 화면에서는 현재 수량과 위치를 빠르게 조회해야 했다. 동시에 현재 값이 어떤 변경을 거쳐 만들어졌는지 확인하고, Engine을 거치지 않은 변경을 발견할 수 있으면 충분했다.

따라서 기존 `orchid_groups` 테이블은 현재 상태의 기준으로 유지했다. Mutation Ledger는 상태를 대신하는 저장소가 아니라 변경 과정을 설명하고 검증하기 위한 이력으로 두었다.

```text
orchid_groups
= 현재 상태의 기준

Mutation Ledger
= 상태 변경 과정과 정합성을 확인하는 이력
```

각 난 묶음에는 `stateRevision`을 두었다. 정상적인 변경은 이전 revision과 다음 revision이 끊기지 않고 이어져야 한다.

```text
BASELINE rev0
      ↓
CHANGE 0 → 1
      ↓
CHANGE 1 → 2
      ↓
CHANGE 2 → 3
```

앞 변경의 `afterState`는 다음 변경의 `beforeState`와 같아야 하고, 마지막 `afterState`는 현재 DB의 난 묶음과 일치해야 한다.

누군가 Engine을 거치지 않고 DB의 현재 값만 수정하면 마지막 Mutation과 현재 상태가 달라진다. 이 차이는 이후 reconciliation 과정에서 발견할 수 있다.

단순한 작업 로그가 누가 무엇을 요청했는지를 남긴다면, Mutation Ledger는 현재 데이터가 기록된 변경의 결과인지까지 확인하기 위한 장치다.

> [시각자료 제안] 실제 난 묶음 한 건을 비식별화해 `rev0 → rev1 → rev2`의 before/after snapshot과 현재 DB 상태를 연결한 그림. 개념도만 제시하는 것보다 실제 reconciliation 결과 일부를 함께 보여주면 신뢰도가 높아진다.

## 경계를 나눈 뒤에야 엔진의 역할이 보였다

이번 구조 변경의 핵심은 Mutation Engine이라는 새로운 이름을 붙인 데 있지 않았다.

Work, Sales와 Inbound는 각자의 업무 규칙을 판단한다. Farm은 난 묶음을 변경할 수 있는 방법과 변경 과정의 정합성을 관리한다. Analytics는 다른 모듈의 Entity나 QueryDSL 타입 대신 필요한 조회 계약을 사용한다.

상태를 바꾸는 방법을 한곳에 모으면서도 변경의 이유는 각 업무 모듈에 남겼다. 덕분에 새로운 작업을 추가할 때 Engine의 잠금과 이력 저장 방법을 다시 구현하지 않아도 되고, Engine 역시 새로운 작업의 세부 규칙을 알 필요가 없어졌다.

다만 이 구조에 도달하는 과정에서 경계를 강하게 나누는 것 자체가 목표가 된 시기도 있었다. 다음 글에서는 작은 wrapper와 adapter가 오히려 코드 이해를 어렵게 만든 과정, 과거 이력과 Shadow Mode를 구현했다가 제거한 이유를 정리한다.
