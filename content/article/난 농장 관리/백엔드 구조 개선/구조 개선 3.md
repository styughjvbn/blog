Mutation Engine의 구현과 단위 테스트가 끝났다고 해서 실제 운영 DB를 새로운 구조로 바꿀 수 있는 것은 아니었다.

이번 변경은 애플리케이션 내부의 호출 구조만 바꾸는 리팩터링이 아니었다. 기존 난 묶음에 revision을 부여하고, 과거 변경을 Mutation Ledger로 옮기며, 앞으로는 Engine을 거치지 않은 쓰기를 차단해야 했다.

코드가 정상적으로 동작하는지뿐 아니라 기존 운영 데이터가 새로운 규칙을 만족하는지와 실제 PostgreSQL에서 동시 요청이 어떻게 처리되는지도 확인해야 했다.

## 실제 PostgreSQL에서 드러난 동시성 문제

기존 테스트만으로는 데이터베이스의 잠금과 제약 조건을 충분히 확인하기 어려웠다.

리팩터링 과정에서 다음과 같은 동시성 문제가 발견됐다.

* Settlement 최초 설정을 동시에 생성할 때 UNIQUE 제약 조건이 충돌했다.
* 품종과 자재 코드를 동시에 발급하면 같은 값을 선택할 가능성이 있었다.
* 하나의 Mutation에서 여러 난 묶음을 생성할 때 write context가 섞였다.
* 동일한 Work Command가 병렬로 실행될 수 있었다.
* 같은 Work Effect가 두 번 적용될 수 있었다.

이 문제들은 메서드를 한 번씩 호출하는 단위 테스트에서는 나타나지 않았다. H2와 PostgreSQL은 잠금, 트랜잭션과 제약 조건을 처리하는 방식에도 차이가 있기 때문에 운영 DB에서 기대하는 동작을 H2 통과만으로 보장할 수 없었다.

따라서 PostgreSQL을 사용하는 테스트 환경을 별도로 구성하고 다음 조건을 직접 검증했다.

* 같은 행을 변경하는 병렬 요청의 row lock
* 여러 난 묶음을 함께 바꿀 때의 lock 순서
* UNIQUE constraint 충돌 처리
* 작업 중간에 실패했을 때의 전체 rollback
* 같은 Command와 Effect가 동시에 들어올 때의 멱등성

중요한 것은 테스트의 개수가 아니라 운영에서 사용하는 저장소의 동시성 의미를 테스트에서도 같게 가져가는 것이었다.

## 운영 백업을 이용한 전환 rehearsal

테스트용 데이터만으로 migration을 확인하면 실제 운영 DB에 쌓인 예외를 놓칠 수 있다.

운영 DB의 백업을 별도 PostgreSQL 데이터베이스에 복원하고 실제 전환과 같은 순서로 rehearsal을 진행했다.

```text
운영 백업 복원
→ Flyway migration
→ 과거 state chain 생성
→ Engine ACTIVE 전환
→ DB write fence 적용
→ 주요 작업 시나리오 실행
→ UI smoke test
→ reconciliation
```

과거 난 묶음은 복원 가능한 작업 이력을 기준으로 `BASELINE`, `CREATE`, `CHANGE`, `DELETE` 체인으로 변환했다. 각 체인의 revision이 이어지는지, 마지막 snapshot과 현재 난 묶음이 같은지 전체 데이터에서 검사했다.

최종 전환 조건은 reconciliation 결과로 정했다.

```text
ready=true
issues=[]
```

검사 항목에 문제가 하나라도 남아 있으면 Engine을 활성화하지 않았다.

## migration으로 발견한 숨은 쓰기 경로

rehearsal에서는 단위 테스트에서 발견하지 못한 기존 쓰기 경로도 확인됐다.

기존 Inbound 로직은 난 묶음을 먼저 INSERT한 뒤 일부 값을 UPDATE했다. Legacy 구조에서는 정상적으로 동작했지만, Engine-only 상태에서 직접 UPDATE를 차단하는 write fence와 충돌했다.


처음 INSERT할 때 필요한 값을 모두 넣도록 변경해 두 번의 쓰기를 하나의 INSERT로 정리했다.

이 문제는 migration SQL 자체의 오류는 아니었다. 새로운 제약을 실제 운영 흐름에 적용하면서 기존 코드에 남아 있던 우회 경로가 드러난 경우였다.

운영 백업 rehearsal은 과거 데이터를 변환할 수 있는지만 확인하는 과정이 아니라, 새 구조에서 허용되지 않는 애플리케이션의 쓰기 경로를 찾는 역할도 했다.

## ACTIVE 이후의 복구 전략

일반적인 애플리케이션 배포에서는 새 버전에 문제가 생기면 이전 이미지를 다시 실행하는 방식으로 rollback할 수 있다.

하지만 DB가 Engine ACTIVE 상태로 전환된 뒤에는 예전 애플리케이션만 다시 실행해서는 안 된다. Legacy writer는 Mutation Ledger를 남기지 않기 때문이다.

```text
DB는 Engine ACTIVE
+
애플리케이션은 Legacy writer
= 현재 상태와 Mutation Ledger가 어긋날 수 있음
```

따라서 ACTIVE 이후에는 수정한 버전을 다시 배포하는 roll-forward를 기본 대응으로 정했다. DB까지 되돌려야 한다면 애플리케이션 이미지뿐 아니라 전환 직전의 DB 상태와 설정을 함께 복원해야 했다.

실제 전환은 다음 순서로 진행했다.

```text
Backend 중지
→ 운영 DB 최종 backup
→ Engine candidate DB 복원
→ schema / row / ledger 검증
→ 기존 운영 DB 이름 변경
→ candidate DB를 production 이름으로 변경
→ writer version ConfigMap 갱신
→ 새 Backend 이미지 시작
→ smoke test
→ reconciliation
```

기존 운영 DB는 바로 삭제하지 않고 다른 이름으로 보존했다. 전환 직전 dump와 당시 deployment, ConfigMap 자료도 함께 남겨 애플리케이션과 데이터의 조합을 다시 만들 수 있도록 했다.

## 코드량보다 책임과 조회 비용

이번 리팩터링은 전체 코드 줄 수를 줄이기 위한 작업은 아니었다. formatter 영향을 제외하면 구조 변경 후 전체 코드량이 크게 감소했다고 보기도 어렵다.

대신 책임이 섞여 있던 서비스와 조회 경로에서는 변화가 있었다.

`WorkOperationDetailService`는 408줄에서 89줄로 줄었고, `AnalyticsQueryService`는 201줄에서 156줄로 책임을 축소했다.

조회 쿼리도 함께 측정했다.

```text
Farm 난 묶음 목록 50건
101 SQL → 약 3 SQL

Work 분석
6 SQL → 2 SQL

재고 분석
2 SQL → 1 SQL
```

반면 일부 Analytics 조회는 다른 모듈의 QueryDSL 타입을 직접 사용하지 않도록 경계를 나누면서 SQL 수가 증가했다. 이 부분은 전체를 성능 개선이라고 묶지 않고 모듈 경계와 조회 비용 사이의 trade-off로 남겼다.

## 단계별 검증 범위

작업을 시작할 때는 기본 테스트 190개가 통과하고 49개가 비활성화된 상태였다.

구조 리팩터링을 마친 시점에는 기본 테스트 459개, PostgreSQL 테스트 98개와 benchmark 2개가 통과했고 실패하거나 비활성화된 테스트는 없었다. 이후 Engine 전환 rehearsal 시점에는 기본 테스트 460개와 PostgreSQL 테스트 96개가 통과했다. 이 둘을 합친 전체 백엔드 테스트는 556개다.

테스트 수가 늘어난 것만으로 구조의 안전성을 증명할 수는 없다. 그래서 검증 단계를 다음처럼 나누었다.

```text
업무 규칙 단위 테스트
→ PostgreSQL 통합·동시성 테스트
→ 운영 백업 migration rehearsal
→ 주요 UI smoke test
→ 전체 데이터 reconciliation
```

서로 다른 단계가 서로 다른 실패를 확인하도록 했다. 테스트 코드가 예상한 시나리오와 운영 데이터에 이미 존재하는 상태를 함께 검사한 뒤 실제 전환을 진행했다.

## Engine-only 전환 이후

최종적으로 실제 운영 PostgreSQL을 Legacy writer에서 Engine-only 구조로 전환했다. 전환 후 상태는 다음 조건을 만족했다.

```text
ACTIVE
ready=true
issues=[]
```

운영 이전 DB와 dump도 복구 자산으로 별도 보존했다.

이번 작업을 통해 코드 안에서 책임을 나누는 것과 운영 데이터를 새로운 책임 구조에 맞게 옮기는 것은 별개의 일이라는 점을 확인했다. 컴파일과 테스트가 통과해도 기존 데이터의 이력이 끊기거나, 이전 애플리케이션이 새로운 DB 규칙을 우회하면 전환은 끝난 것이 아니다.

구조 개선의 원래 목적은 새로운 기능을 추가할 때 기존 코드의 수정 범위를 줄이는 것이었다. 따라서 실제 성공 여부는 다음 작업 유형을 추가할 때 확인할 수 있다.

* 새 Handler만 추가하면 되는가
* 기존 switch와 조건문이 다시 늘어나는가
* Mutation Engine의 공통 실행부를 수정해야 하는가
* 다른 모듈의 내부 구현을 알아야 하는가
* 기존 파일을 몇 개나 함께 수정하는가

앞으로는 신규 기능을 추가할 때 이 항목을 기록하려 한다. Mutation API의 p50과 p95, 트랜잭션 시간과 lock wait도 기준값을 수집하고, reconciliation은 전환 시점의 일회성 검사에서 정기적인 invariant 검사로 이어갈 예정이다.

좋은 아키텍처인지는 사용한 패턴의 수보다 다음 변경에서 확인해야 한다. 이번 작업은 새로운 구조를 완성한 기록이라기보다, 변경 범위와 검증 비용을 측정할 수 있는 출발점을 만든 과정에 가깝다.
