난 묶음의 상태 변경을 Mutation Engine으로 통합하면서 백엔드 모듈의 경계도 함께 정리했다.

각 업무 모듈이 다른 모듈의 Entity를 직접 사용하지 않게 하고, 필요한 값은 명시적인 계약을 통해 주고받도록 했다. 방향 자체는 맞다고 생각했지만 처음 만든 결과가 곧바로 좋은 구조가 된 것은 아니었다.

오히려 한 시점에는 리팩터링 전보다 파일과 계층이 더 많아졌다.

## 의존성을 줄이자 파일이 늘어났다

초기에는 모듈 사이의 직접 의존을 없애는 데 집중했다.

Entity를 직접 전달하던 자리에 작은 wrapper와 command, result 객체를 만들었다. 호출 관계를 끊기 위해 adapter와 interface도 추가했다. 각 타입에는 역할이 있었고 개별 코드만 보면 경계도 이전보다 분명해 보였다.

하지만 하나의 업무 흐름을 따라가면 다른 문제가 나타났다.

값 하나를 wrapper에 넣고 다음 계층에서 바로 꺼냈다. 구현이 하나뿐이고 달라질 가능성도 확인되지 않은 interface를 거쳐 실제 코드로 이동했다. 단순히 메서드 하나를 전달하기 위한 adapter도 생겼다.

그 결과 한 시점에는 운영 Java 코드가 약 276줄 증가했고 파일 수도 562개에서 576개로 늘어났다. 줄 수와 파일 수의 증가 자체가 실패를 의미하지는 않지만, 실제 업무를 이해하기 위해 열어야 하는 파일이 많아졌다는 점은 문제였다.

처음에는 다음 질문을 가장 중요하게 봤다.

```text
다른 모듈에 대한 의존성이 줄었는가?
```

이후에는 질문을 더 늘렸다.

```text
하나의 업무 흐름을 이해하려면 몇 파일을 봐야 하는가?

호출을 몇 단계 따라가야 실제 변경을 찾을 수 있는가?

새로운 기능을 추가할 때 기존 코드를 얼마나 수정하는가?

이 추상화에는 실제로 달라질 가능성이 있는가?
```

이 기준으로 다시 확인해 ID 하나만 감싸는 wrapper, 단순 전달만 하는 adapter와 구현 변형이 없는 interface를 제거했다. 메서드 하나로 충분한 부분은 별도 클래스로 만들지 않았다.

모듈 경계를 유지하는 데 필요한 계약은 남겼지만, 계층의 수 자체를 설계 품질로 보지는 않게 되었다.

## 과거 이력을 자세히 남기려다 예외가 늘어났다

새로운 Engine을 적용한 뒤 발생하는 변경은 처음부터 같은 규칙으로 기록할 수 있었다. 더 어려운 문제는 이미 운영 DB에 저장된 난 묶음과 작업 이력이었다.

처음에는 기존 난 묶음의 현재 상태를 `BASELINE revision 0`으로 만들고, 전환 이후의 변경부터 이어서 기록하려 했다. 구현은 단순하지만 Engine 이전 작업과 현재 상태가 어떻게 연결되는지 설명할 수 없었다.

과거 작업을 최대한 복구하기 위해 `HistoricalEvidence`라는 별도 구조를 설계했다. 구조가 복잡해지자 다시 `HISTORICAL` Entry 하나로 합쳤다.

그러나 이름을 하나로 줄인 뒤에도 예외는 사라지지 않았다.

```text
HISTORICAL에도 revision이 있어야 하는가?

snapshot을 복원할 수 없으면 어떻게 기록하는가?

reconciliation에서 정상 체인으로 검사해야 하는가?

일반 CHANGE와 다른 규칙은 어디까지 허용하는가?
```

과거 데이터를 설명하기 위한 타입 하나 때문에 이력 전체의 규칙이 두 갈래로 나뉘기 시작했다.

결국 `HISTORICAL`을 제거했다. 복원할 수 있는 과거 이력은 현재와 같은 state chain으로 변환하고, Entry 종류도 다음 네 가지로 제한했다.

```text
BASELINE
CREATE
CHANGE
DELETE
```

과거라는 이유로 별도의 의미 체계를 유지하기보다 복원 가능한 범위와 그렇지 않은 범위를 migration 과정에서 분명하게 다루기로 했다.

처음 만든 모델을 유지하는 것보다 예외 규칙이 계속 늘어나는지를 보는 편이 더 중요했다.

## 안전해 보였던 Shadow Mode도 제거했다

운영에서 Legacy 방식 대신 Mutation Engine을 바로 사용하기에는 위험이 크다고 생각했다. 그래서 한때 Shadow Mode를 구현했다.

```text
Legacy
→ 실제 상태 변경

Mutation Engine
→ 분리된 객체에서 같은 요청 계산

Legacy 결과와 Engine 결과
→ 비교
```

기존 코드가 실제 데이터를 변경하고 Engine은 같은 입력의 결과만 계산한다. 두 결과를 비교하면 운영에 영향을 주지 않고 새로운 로직을 검증할 수 있다고 판단했다.

사용량이 많은 서비스라면 유효한 방식이다. 하지만 농장 관리 시스템은 사용자와 구조 변경 작업의 수가 많지 않다. 충분한 사례가 쌓이기를 기다리면 검증 기간이 지나치게 길어지고, 드물지만 중요한 분주·합식 같은 작업은 오랫동안 실행되지 않을 수도 있었다.

코드가 이미 만들어져 있었지만 Shadow Mode를 제거하고 실제 운영 백업을 이용한 rehearsal로 방향을 바꾸었다.

```text
운영 DB 백업 복원
→ 주요 작업 시나리오 실행
→ Engine 결과 확인
→ 전체 데이터 reconciliation
```

기다리는 대신 통제된 환경에서 필요한 시나리오를 직접 실행했다. 현재 시스템의 사용량에서는 이 방식이 더 짧은 시간 안에 많은 실패 조건을 확인할 수 있었다.

## 멱등성도 하나의 키로 합치지 않았다

구조를 단순하게 만들려는 과정에서 request key, effect key와 Mutation의 멱등성을 하나로 합칠 수 있을지도 검토했다.

하지만 같은 요청이 반복되는 것과 이미 만들어진 작업 결과가 다시 적용되는 것은 다른 문제였다.

```text
사용자 요청
    ↓
WorkOperation
    ↓
WorkAppliedEffect
    ↓
OrchidGroupMutation
    ↓
MutationEntry
```

사용자가 저장 버튼을 다시 누르거나 네트워크 재시도로 같은 명령이 들어오는 경우에는 Command 단위의 중복을 막아야 한다. 반면 이미 생성된 Work Effect가 재처리되는 경우에는 Effect 단위에서 난 묶음의 변경이 다시 적용되지 않도록 해야 한다.

두 중복은 생명주기와 실패 지점이 다르기 때문에 하나의 키로 합치지 않았다.

Command 수준에서는 `work_command_receipts`로 요청을 보호하고, Effect 수준에서는 operation과 effect key를 별도로 확인했다. 동일한 idempotency key가 들어와도 요청 내용의 fingerprint가 다르면 같은 요청으로 재사용하지 않고 충돌로 처리했다.

fingerprint를 만드는 과정에서는 `Set`의 순회 순서에 따라 같은 내용도 다른 문자열이 될 수 있는 문제도 발견했다. 비교 전에 입력값을 일정한 순서로 정렬하는 canonicalization을 적용해 논리적으로 같은 요청이 같은 fingerprint를 만들도록 했다.

겉으로는 멱등성이라는 하나의 문제처럼 보였지만 실제로 보호하는 대상이 달랐다. 단순화는 이름과 구현을 합치는 것이 아니라 실패 모델을 구분한 뒤 불필요한 부분을 없애는 일에 가까웠다.

## 구현한 코드도 판단이 바뀌면 제거했다

이번 리팩터링에서는 설계 문서에서만 검토한 것이 아니라 실제로 만든 구조를 여러 번 제거했다.

* 경계를 나누기 위해 추가한 wrapper와 adapter를 줄였다.
* 과거 이력을 표현하던 `HistoricalEvidence`와 `HISTORICAL` Entry를 없앴다.
* 운영 검증을 위해 만든 Shadow Mode를 rehearsal 방식으로 바꿨다.
* 하나로 합치려던 멱등성은 실패 지점에 따라 다시 나눴다.

공통된 기준은 해당 패턴이 일반적으로 좋은지가 아니었다. 현재 시스템에서 변경 비용과 검증 비용을 실제로 줄이는지를 확인했다.

다만 구조가 단순해졌다는 판단만으로 운영 전환을 승인할 수는 없었다. 난 묶음의 변경 경로가 달라지고 기존 데이터에 revision과 이력을 추가하는 작업이었기 때문이다.

다음 글에서는 H2가 아닌 PostgreSQL에서 동시성을 검증한 이유, 운영 백업을 사용한 migration rehearsal과 실제 서비스 DB를 Engine-only 구조로 전환한 과정을 정리한다.
