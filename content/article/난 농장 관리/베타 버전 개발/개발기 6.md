지난 글에서는 Green-house 베타 버전을 어떤 기술 스택과 아키텍처로 구현했는지 정리했다.

프론트엔드는 Next.js, 백엔드는 Spring Boot, 데이터베이스는 PostgreSQL을 사용했다.
백엔드는 MSA로 나누지 않고, 하나의 애플리케이션 안에서 `farm`, `work`, `sales`, `auction`, `payment` 같은 도메인 경계를 나누는 모듈러 모놀리스 구조로 구성했다.

이번 글에서는 베타 버전을 실제로 배포하면서 정리한 내용을 남겨보려 한다.

## 베타 버전 배포의 목표

이번 배포의 목표는 거창하지 않았다.

처음부터 대규모 트래픽을 처리하거나, 무중단 배포를 완벽하게 구성하거나, 복잡한 모니터링 시스템을 붙이는 것이 목표는 아니었다.

우선 중요한 것은 다음이었다.

```text id="f9tl33"
1. 실제 서버에서 프론트엔드와 백엔드가 동작할 것
2. PostgreSQL 데이터가 유지될 것
3. 외부에서 서비스에 접속할 수 있을 것
4. 배포 과정을 반복 가능하게 만들 것
5. 장애가 나도 최소한 복구할 수 있을 것
```

즉, 베타 버전 배포의 핵심은 "멋진 인프라"가 아니라 **운영 가능한 상태를 만드는 것**이었다.

## 로컬 실행 기준 정리

배포 전에 먼저 로컬 실행 흐름을 정리했다.

개발 환경에서 실행하는 기본 흐름은 다음과 같다.

```bash
# DB 실행
docker compose up -d db

# backend 실행
cd backend
./gradlew bootRun

# frontend 실행
cd frontend
npm install
npm run dev
```

베타 버전이 커지면서 로컬 실행 방법도 문서화가 필요해졌다.

처음에는 그냥 기억에 의존해도 됐다.
하지만 백엔드, 프론트엔드, DB, 환경 변수가 나뉘기 시작하면서 실행 순서와 필요한 값을 정리하지 않으면 나중에 다시 세팅할 때 헷갈릴 수밖에 없었다.

## 환경 변수 분리

배포 환경에서는 환경 변수를 분리해야 했다.

백엔드에는 DB 연결 정보와 파일 저장 경로가 필요했다.

```text id="3b4mt8"
SPRING_DATASOURCE_URL
SPRING_DATASOURCE_USERNAME
SPRING_DATASOURCE_PASSWORD
SPRING_PROFILES_ACTIVE
FILE_STORAGE_PATH
```

프론트엔드에는 API 서버 주소가 필요했다.

```text id="hmtdmc"
NEXT_PUBLIC_API_BASE_URL
```

로컬에서는 대충 맞춰서 실행할 수 있지만, 운영에서는 환경 변수를 명확히 분리해야 한다.
특히 DB 계정이나 비밀번호 같은 값은 코드에 직접 넣으면 안 된다.

이번 베타 버전에서는 복잡한 비밀 관리 시스템까지 붙이기보다는, 배포 환경에서 필요한 값을 분리해서 관리하는 것부터 시작했다.

## 이미지 빌드와 배포 흐름

프론트엔드와 백엔드는 각각 컨테이너 이미지로 빌드했다.

GitHub Actions를 통해 `main`, `develop`, 태그 푸시 시 이미지를 만들고, GHCR에 업로드하는 흐름을 구성했다.

```text id="b1m5co"
GitHub push
  ↓
GitHub Actions
  ↓
Docker image build
  ↓
GHCR push
  ↓
서버에서 이미지 배포
```

처음에는 서버에서 직접 코드를 pull 받고 빌드하는 방식도 가능했다.
하지만 배포를 반복할수록 서버에서 직접 빌드하는 방식은 관리가 불편해진다.

그래서 이미지는 GitHub Actions에서 만들고, 서버에서는 만들어진 이미지를 받아 실행하는 구조로 잡았다.

이렇게 하면 배포 서버에는 빌드 환경을 덜 설치해도 되고, 어떤 코드가 어떤 이미지로 배포되었는지도 추적하기 쉬워진다.

## 운영 서버 구성

초기 운영 환경은 다음 구성을 기준으로 잡았다.

```text id="89d4q5"
Nginx
 ├─ frontend
 └─ backend

PostgreSQL
```

사용자는 Nginx를 통해 프론트엔드에 접속하고, 프론트엔드는 백엔드 API를 호출한다.
백엔드는 PostgreSQL에 운영 데이터를 저장한다.

```text id="6cevg6"
사용자
  ↓
Nginx
  ↓
Frontend
  ↓
Backend
  ↓
PostgreSQL
```

외부 접속이 필요하기 때문에 HTTPS 적용도 고려 대상이었다.
내부망에서만 쓴다고 해도 DB 백업은 반드시 분리해서 보관해야 했다.

## 헬스체크

운영에서는 서버가 "떠 있다"는 것과 "정상적으로 요청을 처리할 수 있다"는 것이 다르다.

그래서 백엔드에는 헬스체크 엔드포인트를 두고, 배포 환경에서 readiness/liveness probe를 통해 상태를 확인하도록 했다.

예를 들어 백엔드는 다음 경로로 상태를 확인할 수 있다.

```bash
curl -i http://green-house-backend:8080/actuator/health
```

헬스체크는 단순해 보이지만 운영에서는 꽤 중요하다.

서버 프로세스는 떠 있지만 DB 연결이 안 되거나, 애플리케이션 초기화가 끝나지 않은 상태에서 요청을 받으면 문제가 생길 수 있기 때문이다.

베타 버전에서는 최소한의 헬스체크를 통해 배포 후 서비스 상태를 확인할 수 있도록 했다.

## 운영 전 체크리스트

베타 버전 배포 전에는 체크리스트를 만들었다.

운영 데이터가 들어가기 시작하면 단순히 "화면이 열린다"만 확인해서는 부족하다.
농장 관리 시스템은 데이터가 핵심이기 때문에, 주요 흐름이 실제로 동작하는지 확인해야 했다.

```text id="73eimm"
DB 마이그레이션 정상 실행
15개 동 / 45개 다이 / 90개 구역 생성 확인
난 묶음 등록 / 수정 / 삭제 확인
난 묶음 이동 시 작업 이력 생성 확인
작업 이력 등록 / 조회 확인
판매 전표 생성 / 출력 확인
경매 lot 조회 / 상태 변경 확인
경매 정산 생성 / 입금 확인 확인
거래처 잔액 조회 확인
백업 파일 생성 확인
서버 재시작 후 데이터 유지 확인
```

이 체크리스트를 만든 이유는 단순하다.

배포가 성공했다고 해서 운영 준비가 끝난 것은 아니기 때문이다.
실제로 부모님이 사용하기 전에 최소한 핵심 흐름은 직접 눌러보며 확인해야 했다.

## 백업

이번 프로젝트에서 가장 중요하게 본 운영 요소는 백업이었다.

코드는 다시 작성할 수 있다.
하지만 운영 데이터는 사라지면 복구하기 어렵다.

특히 이 시스템에는 다음 데이터가 계속 쌓인다.

```text id="2zbavv"
난 묶음 위치
작업 이력
품종 정보
입고 기록
판매 전표
경매 lot 상태 이력
정산 기록
입금 이벤트
```

그래서 PostgreSQL 백업을 반드시 고려했다.

기본적인 백업 명령은 다음과 같다.

```bash
pg_dump -U greenhouse greenhouse > backup_$(date +%Y%m%d).sql
```

백업 정책은 다음처럼 잡았다.

```text id="jpoxs4"
매일 1회 백업
최근 7일 보관
월 1회 장기 보관
다른 PC 또는 외장 디스크에 복사
주기적으로 복구 테스트
```

백업은 "파일이 생성된다"에서 끝나면 안 된다.
실제로 복구가 되는지도 확인해야 한다.

운영 데이터가 쌓인 뒤에는 DB가 곧 프로젝트의 핵심 자산이 되기 때문이다.

## 장애 대응 원칙

베타 버전에서는 장애 대응 원칙도 간단하게 정리했다.

```text id="6maw6m"
운영 DB 직접 수정은 최소화한다.
수정 전 백업을 만든다.
전표, 작업 이력, 입금 이벤트, 경매 상태 이력은 삭제하지 않는다.
잘못된 데이터는 취소 또는 보정 이력으로 처리한다.
```

가장 위험한 것은 운영 중에 DB를 직접 수정하는 것이다.

물론 작은 프로젝트에서는 급하면 DB에 직접 들어가서 고치고 싶어진다.
하지만 판매 전표, 경매 lot, 정산, 입금 이벤트처럼 서로 연결된 데이터는 한 곳만 수정하면 오히려 더 꼬일 수 있다.

그래서 운영 중 잘못된 데이터가 생기면 가능하면 시스템의 기능을 통해 취소하거나 보정하는 방향으로 처리하려고 했다.

특히 다음 데이터는 함부로 삭제하지 않는 것이 중요하다.

```text id="f4vdfk"
작업 이력
위치 이동 이력
판매 전표
경매 상태 이력
입금 이벤트
```

이 데이터들은 단순한 현재 상태가 아니라 "무슨 일이 있었는지"를 설명하는 기록이기 때문이다.

## 베타 버전 배포 후 느낀 점

베타 버전 배포를 하면서 가장 크게 느낀 것은, 배포는 개발의 끝이 아니라는 점이었다.

로컬에서 기능이 잘 동작하는 것과 실제 운영 환경에서 안정적으로 쓰는 것은 전혀 다른 문제였다.

```text id="o7qjyl"
환경 변수는 제대로 분리되었는지
DB 마이그레이션은 정상 실행되는지
이미지는 반복해서 빌드할 수 있는지
서버 재시작 후 데이터는 유지되는지
헬스체크는 정상인지
백업은 만들어지는지
복구할 수 있는지
```

기능 구현 중에는 화면과 API에 집중하게 된다.
하지만 실제 운영을 생각하면 배포, 백업, 장애 대응 같은 요소도 결국 시스템의 일부다.

특히 이번 프로젝트는 실제 농장 데이터를 다루기 때문에, 데이터 보존이 가장 중요했다.

## 정리

Green-house 베타 버전은 이제 실제 운영을 시작할 수 있는 상태가 되었다.

아직 부족한 부분은 많다.
화면 UX도 더 다듬어야 하고, 경매 데이터 입력도 더 편하게 만들어야 하고, 판매와 입금 흐름도 운영하면서 계속 개선해야 한다.

하지만 베타 버전 배포를 통해 최소한 다음 기반은 갖추었다.

```text id="5l9r9m"
프론트엔드 / 백엔드 배포
PostgreSQL 운영
GitHub Actions 기반 이미지 빌드
GHCR 이미지 관리
헬스체크
운영 전 체크리스트
DB 백업
장애 대응 원칙
```

이번 글까지가 Green-house 프로젝트 소개 시리즈의 마지막 글이다.

앞으로는 실제 운영하면서 발견한 문제를 하나씩 기록해보려 한다.
입력 실수, 삭제 정책, 경매 반환 처리, 판매 전표 수정, 태블릿 UX, 백업 자동화처럼 운영 중에 마주치는 문제들을 개선 과정 중심으로 정리할 예정이다.
