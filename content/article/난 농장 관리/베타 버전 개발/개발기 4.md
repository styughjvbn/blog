지난 글에서는 일반 판매와 경매 판매를 어떻게 다르게 모델링했는지 정리했다.

일반 판매는 전표 중심으로 관리할 수 있었지만, 경매 판매는 출하, 낙찰, 유찰, 재경매, 반환, 정산, 입금 흐름이 분리되어 있었다.
그래서 경매는 단순 판매 전표가 아니라 lot 단위로 추적하도록 설계했다.

이번 글에서는 베타 버전에서 실제로 구현한 기능들을 화면 중심으로 정리해보려 한다.

## 베타 버전의 목표

베타 버전의 목표는 모든 기능을 완벽하게 만드는 것이 아니었다.
우선 실제 농장에서 사용할 수 있는 최소한의 운영 흐름을 만드는 것이 목표였다.

처음부터 완전 자동화나 정밀 분석을 목표로 하면 개발 범위가 너무 커진다.
그래서 베타 버전에서는 다음 기준을 잡았다.

```text id="84q9qa"
1. 농장 위치를 확인할 수 있어야 한다.
2. 난 묶음을 등록하고 이동할 수 있어야 한다.
3. 작업 이력을 남길 수 있어야 한다.
4. 품종과 입고 기록을 관리할 수 있어야 한다.
5. 일반 판매 전표를 작성할 수 있어야 한다.
6. 경매 출하 lot을 추적할 수 있어야 한다.
7. 정산과 입금 상태를 확인할 수 있어야 한다.
```

기능을 많이 넣는 것보다, 실제 운영 흐름이 끊기지 않는 것이 더 중요했다.

작업 이력은 농장 작업을 기록하는 화면이고, 판매 관리는 일반 판매와 경매 판매, 정산, 입금을 관리하는 화면이다.

## 대시보드

대시보드는 농장의 현재 상태를 빠르게 확인하는 진입 화면이다.

여기서는 세부 수정 기능을 넣기보다, 오늘 확인해야 할 정보를 요약해서 보여주는 것에 집중했다.


## 농장 현황

농장 현황 화면은 전체 농장을 조회하는 화면이다.

베타 버전에서는 농장을 다음 흐름으로 탐색할 수 있도록 했다.

```text id="eic3kp"
전체 농장 보기
  ↓
동 선택
  ↓
물리 다이 선택
  ↓
논리 구역 선택
  ↓
선택 범위의 난 묶음 목록 확인
```

농장 현황에서 가장 중요했던 것은 실제 농장의 공간감을 최대한 유지하는 것이었다.

단순한 표로만 보여주면 개발하기는 쉽지만, 현장 작업자가 보기에는 직관적이지 않다.
부모님은 "3동 2다이 우측"처럼 위치를 기억하고 있기 때문에, 화면에서도 비슷한 방식으로 위치를 찾을 수 있어야 했다.

> 사진 추천: 농장 현황 맵 화면
> 예시 파일명: `farm-status-map.png`

![농장 현황 맵](farm-status-map.png)

농장 현황 화면에서는 데이터 변경을 최소화했다.

처음에는 이 화면에서도 등록, 수정, 이동을 모두 할 수 있게 만들까 고민했다.
하지만 조회 화면과 작업 화면이 섞이면 화면이 복잡해지고 실수 가능성도 커진다.

그래서 농장 현황은 조회 중심으로 두고, 실제 수정이 필요하면 난 묶음 관리 화면으로 이동하는 방식으로 나누었다.

## 난 묶음 관리

난 묶음 관리는 실제 작업 화면이다.

여기서는 난 묶음을 등록하고, 수정하고, 삭제하고, 위치를 이동할 수 있다.

```text id="is40jj"
난 묶음 등록
난 묶음 수정
난 묶음 삭제
같은 동 내부 드래그 이동
다른 동으로 이동
위치 이동 이력 자동 생성
```

베타 버전의 핵심 관리 단위는 개별 화분이 아니라 난 묶음이다.
같은 품종과 상태의 화분들이 함께 이동하고 관리되는 경우가 많기 때문에, 실제 농장 운영 단위에 맞춰 난 묶음 단위로 관리했다.

> 사진 추천: 난 묶음 관리 화면 전체 캡처
> 예시 파일명: `orchid-group-management.png`

![난 묶음 관리](orchid-group-management.png)

난 묶음을 이동하면 단순히 위치만 바뀌는 것이 아니라, 위치 이동 작업 이력이 자동으로 생성된다.

```text id="ygsr9i"
이동 전 위치
이동 후 위치
이동일
작업자
메모
```

위치 이동도 하나의 작업이기 때문이다.
나중에 "이 난이 언제 왜 여기로 이동했는지"를 확인할 수 있어야 했다.

## 작업 이력

작업 이력 화면에서는 농장에서 발생한 작업을 기록한다.

작업은 항상 난 묶음 하나에만 발생하지 않는다.
어떤 작업은 농장 전체에 해당하고, 어떤 작업은 특정 동이나 다이, 구역에 해당한다.

그래서 작업 이력은 여러 대상 단위에 남길 수 있도록 했다.

```text id="4269pc"
농장
동
물리 다이
논리 구역
난 묶음
```

작업 유형은 농장 운영에 맞춰 관리할 수 있도록 했다.

```text id="qx4hh8"
농약
비료
분갈이
상태 기록
일반 메모
잎 정리
잡초 정리
단화/꽃 정리
위치 이동
```

> 예시 파일명: `work-records.png`

운영 데이터는 가능하면 삭제하지 않는 방향으로 잡았다.

## 품종/입고/자재 관리

품종/자재 관리 메뉴에는 품종, 입고, 자재 탭을 두었다.

```text id="6cmgyv"
품종/자재 관리
  ├─ 품종
  ├─ 입고
  └─ 자재
```

품종 탭에서는 품종 기준 정보를 관리한다.

```text id="6plxua"
속
품종명
별칭
기본 화분 크기
판매 사용 여부
상태
보유 묶음 수
총 보유 수량
판매 가능 수량
```

처음에는 난 묶음에 품종명을 문자열로만 저장해도 된다고 생각했다.
하지만 그렇게 하면 같은 품종이 여러 이름으로 입력될 수 있고, 나중에 품종별 판매 성과를 분석하기 어렵다.

그래서 품종은 별도의 기준 정보로 분리했다.

> 사진 추천: 품종 목록 또는 품종 상세 화면
> 예시 파일명: `varieties.png`

![품종 관리](varieties.png)

입고 탭에서는 외부에서 농장으로 들어온 모종이나 상품분을 기록한다.

```text id="xfhrrl"
유리병 모종
포트 모종
상품분
샘플
기타 외부 유입
```

특히 유리병 모종은 바로 다이에 올라가지 않는 경우가 많다.
임시 공간에 보관했다가 포트 작업 후 실제 난 묶음으로 생성되는 흐름이 필요했다.

```text id="6x0u8e"
유리병 모종 입고
  ↓
임시보관
  ↓
포트 작업
  ↓
난 묶음 생성
  ↓
다이에 배치
```

> 예시 파일명: `inbound-records.png`

![입고 관리](inbound-records.png)

자재 탭에서는 약제, 비료, 일반 자재 기준 정보를 관리한다.
자재도 운영 기록과 연결될 수 있기 때문에 삭제보다 비활성화를 우선하는 방향으로 잡았다.

## 판매 관리

판매 관리에서는 일반 판매 전표와 경매 판매 전표를 작성한다.

일반 판매는 거래처와 판매 품목을 기준으로 전표를 만든다.

```text id="ztvavw"
거래처 선택
판매일 입력
판매 품목 입력
수량 / 단가 / 금액 계산
전표 저장
입금 확인
```

전표를 저장할 때 바로 난 묶음 수량을 차감하지는 않는다.
출고가 완료되기 전까지는 예약 수량으로 잡고, 실제 출고 완료 시점에 수량을 차감하는 방식으로 처리했다.

```text id="io8sym"
전표 저장
  → 예약 수량 증가

출고 완료
  → 실제 수량 차감
  → 예약 수량 해제
```

이렇게 한 이유는 전표를 작성했지만 아직 실제로 물건이 나가지 않은 상태가 존재하기 때문이다.

> 사진 추천: 판매 전표 작성 화면
> 예시 파일명: `sales-slip-form.png`

![판매 전표 작성](sales-slip-form.png)

판매 전표는 A5 출력 흐름도 고려했다.
기존 종이 전표 흐름을 완전히 없애기보다, 필요한 경우 출력해서 사용할 수 있도록 했다.

## 경매 추적

경매 추적 화면은 베타 버전에서 가장 중요하게 본 기능 중 하나다.

경매는 일반 판매처럼 전표 하나로 끝나지 않는다.
출하한 물건이 일부만 낙찰될 수도 있고, 유찰 후 다시 경매에 올라갈 수도 있고, 끝내 반환될 수도 있다.

그래서 경매는 lot 단위로 추적한다.

```text id="5ciqx8"
경매 lot
  ├─ 출하 수량
  ├─ 판매 수량
  ├─ 대기 수량
  ├─ 반환 수량
  ├─ 현재 상태
  ├─ 경매 시도
  └─ 상태 이력
```

경매 결과 입력에서는 낙찰, 부분 낙찰, 유찰, 반환 추정 같은 결과를 기록할 수 있도록 했다.

```text id="stkm7c"
낙찰
부분 낙찰
유찰
반환 추정
반환 확인
수량 보정
```

> 예시 파일명: `auction-lots.png`

![경매 lot 목록](auction-lots.png)

> 사진 추천: 경매 lot 상세 또는 결과 입력 화면
> 예시 파일명: `auction-lot-detail.png`

![경매 lot 상세](auction-lot-detail.png)

이 기능을 통해 "얼마를 팔았는지"뿐만 아니라 "어떤 물건이 아직 경매장에 남아 있는지", "어떤 물건이 반환되어야 하는지"까지 확인할 수 있게 했다.

## 정산과 입금 관리

판매와 경매는 결국 입금 확인까지 이어져야 한다.

일반 판매는 판매 전표 단위로 입금을 확인할 수 있다.
경매 판매는 경매장별 정산 묶음을 기준으로 입금을 확인한다.

```text id="u7nmu8"
일반 판매
  → 판매 전표 입금 확인

경매 판매
  → 경매 정산 생성
  → 정산 입금 확인
```

입금 이벤트는 삭제하지 않고 보존하는 방향으로 설계했다.
돈과 관련된 기록은 나중에 다시 확인해야 할 가능성이 높기 때문이다.

```text id="fz6mkw"
입금 수신
부분 입금
초과 입금
보정
취소
```

거래처별 잔액도 확인할 수 있도록 했다.

```text id="a9a0ub"
거래처
미입금 금액
선수금
대상 미지정 입금
잔액
```

## 베타 버전에서 하지 않은 것

베타 버전에서 일부러 하지 않은 것도 있다.

```text id="p27c63"
개별 화분 전수 관리
정밀 CAD 수준의 좌표 편집
완전 자동 재고 차감
자동 입금 확정 처리
AI 진단 기능
```

이 기능들은 있으면 좋아 보이지만, 초기에 넣기에는 비용이 크고 실제 운영 안정성을 해칠 수 있다고 판단했다.

특히 개별 화분 전수 관리는 가장 고민이 많았다.
하지만 실제 농장에서는 묶음 단위로 움직이는 경우가 많고, 모든 화분에 QR을 붙여 관리하는 것은 초기 운영 부담이 너무 컸다.

그래서 베타 버전에서는 "정교하지만 쓰기 어려운 시스템"보다 "조금 거칠어도 실제로 쓸 수 있는 시스템"을 우선했다.

## 정리

베타 버전은 완성형 시스템이 아니다.

하지만 실제 농장의 운영 흐름을 웹에서 관리하기 위한 기본 뼈대는 만들었다.
