지난 글에서는 Green-house 베타 버전에서 구현한 기능들을 화면 중심으로 정리했다.

베타 버전에서는 농장 현황, 난 묶음 관리, 작업 이력, 품종/입고 관리, 판매 관리, 경매 추적, 정산/입금 관리까지 실제 운영에 필요한 흐름을 우선 구현했다.

이번 글에서는 이 시스템을 어떤 기술 스택과 아키텍처로 구현했는지 정리해보려 한다.

## 전체 구조

프로젝트는 크게 프론트엔드, 백엔드, 문서, 배포 설정으로 나누었다.

```text id="mglf6w"
green-house/
 ├─ backend/
 ├─ frontend/
 ├─ docs/
 └─ docker-compose.yml
```

처음부터 복잡한 구조를 만들기보다는, 프론트엔드와 백엔드를 명확히 분리하고 문서를 함께 관리하는 방향으로 잡았다.

농장 운영 시스템은 기능이 많다.

```text id="hii0s3"
농장 구조
난 묶음
작업 이력
품종
입고
자재
거래처
판매 전표
경매 lot
경매 정산
입금 이벤트
```

이 기능들은 서로 독립적이면서도 연결되어 있다.
예를 들어 판매 전표는 난 묶음의 예약 수량에 영향을 주고, 경매 정산은 거래처와 입금 이벤트로 이어진다.

그래서 단순 CRUD 프로젝트처럼 한두 개의 화면만 관리하는 구조로는 부족했다.

## 프론트엔드: Next.js

프론트엔드는 Next.js를 사용했다.

처음에는 단순 React로도 충분하지 않을까 생각했지만, 실제로는 화면이 많고 라우팅 구조가 필요했다.
대시보드, 농장 현황, 난 묶음 관리, 작업 이력, 품종/자재 관리, 판매 관리, 분석, 설정처럼 메뉴 단위가 분명했기 때문이다.

```text id="zo4qmg"
대시보드
농장 현황
난 묶음 관리
작업 이력
품종/자재 관리
판매 관리
분석
설정
```

Next.js를 사용하면서 라우트 단위로 화면을 나누고, 각 화면의 데이터 조회 흐름을 정리할 수 있었다.

기술 스택은 다음과 같이 잡았다.

```text id="i1hh7p"
Next.js
TypeScript
Tailwind CSS
React 기반 상태 관리
```

TypeScript는 필수에 가까웠다.
도메인 타입이 많고, API 응답 구조도 복잡했기 때문이다.

예를 들어 난 묶음 하나만 해도 단순히 이름과 수량만 있는 것이 아니다.

```text id="gb8uy0"
난 묶음 ID
품종 ID
속
품종명
수량
예약 수량
화분 크기
연차
상태
위치
세그먼트 배치
메모
```

경매 lot은 더 복잡하다.

```text id="qaz9ki"
출하일
경매장
품목
품종
등급
출하 수량
판매 수량
대기 수량
반환 수량
현재 상태
경매 시도 목록
상태 이력
```

이런 데이터를 JavaScript 객체로만 다루면 화면이 커질수록 실수가 많아질 것 같았다.
그래서 프론트엔드에서도 타입을 명확히 두는 방향으로 진행했다.

## 기능 중심 폴더 구조

프론트엔드는 기능 중심 구조로 정리했다.

```text id="zfzjyc"
src/
 ├─ app/
 ├─ features/
 ├─ entities/
 ├─ shared/
 └─ widgets/
```

각 폴더의 역할은 다음과 같다.

```text id="r7qyw8"
app
  → 라우트 진입점

features
  → 기능 단위 화면, 상태, API 호출

entities
  → 여러 기능에서 공유하는 도메인 타입

shared
  → 공통 UI, API 유틸, 공통 함수

widgets
  → 앱 쉘처럼 큰 공통 레이아웃
```

중요하게 본 것은 `app` 폴더를 얇게 유지하는 것이었다.
Next.js App Router를 사용하면 `page.tsx`에 이것저것 넣기 쉽다.
하지만 그렇게 하면 화면이 커질수록 유지보수가 어려워진다.

그래서 `app/*/page.tsx`는 라우트 진입점 역할만 하고, 실제 화면과 상태 로직은 `features` 내부로 옮기는 방향을 잡았다.

```text id="mz8u7q"
app/farm-status/page.tsx
  → FarmStatusPage 호출

features/farm-status/
  → 실제 농장 현황 화면 구현
  → API 호출
  → 화면 상태 관리
  → 하위 컴포넌트
```

이 구조는 처음에는 조금 번거롭지만, 기능이 늘어날수록 효과가 있었다.

## 백엔드: Spring Boot

백엔드는 Spring Boot를 사용했다.

농장 관리 시스템은 화면보다 도메인 규칙이 더 중요했다.
판매 전표를 저장할 때 예약 수량을 어떻게 반영할지, 경매 lot 상태를 어떻게 바꿀지, 입금 이벤트를 어떻게 남길지 같은 규칙이 계속 생겼다.

이런 흐름은 백엔드에서 명확하게 관리하는 편이 좋다고 판단했다.

기술 스택은 다음과 같다.

```text id="magt8y"
Spring Boot
Java 21
Spring Data JPA
Bean Validation
PostgreSQL
Flyway Migration
```

Spring Boot를 선택한 이유는 익숙함도 있었지만, 트랜잭션 처리와 도메인 규칙을 안정적으로 관리하기 좋았기 때문이다.

예를 들어 경매 결과를 입력하는 과정은 단순히 결과 행 하나를 저장하는 일이 아니다.

```text id="2db6fo"
경매 lot 조회
경매 시도 생성
경매 결과 행 생성
판매 수량 계산
대기 수량 계산
현재 상태 변경
상태 이력 생성
필요 시 정산 대상 반영
```

이런 작업은 하나의 트랜잭션 안에서 처리되어야 한다.
중간에 일부만 저장되면 데이터가 꼬일 수 있기 때문이다.

## MSA가 아니라 모듈러 모놀리스

처음에는 판매, 경매, 입금 기능을 따로 서비스로 나누는 것도 고민했다.

특히 판매 관리 쪽은 생각보다 도메인이 컸다.
일반 판매, 경매 출하, lot 추적, 정산, 입금 이벤트까지 모두 연결되기 때문이다.

하지만 베타 버전에서는 MSA로 나누지 않았다.

대신 하나의 백엔드 애플리케이션 안에서 모듈 경계를 나누는 **모듈러 모놀리스** 구조를 선택했다.

```text id="g27x3k"
common
farm
work
partner
sales
auction
payment
print
```

각 모듈의 역할은 다음과 같이 잡았다.

```text id="r2f4jm"
common
  → 공통 응답, 예외 처리, 공통 검증

farm
  → 동, 다이, 구역, 난 묶음, 품종, 입고, 자재

work
  → 작업 유형, 작업 이력, 위치 이동 이력

partner
  → 거래처, 거래처 정산 설정

sales
  → 판매 전표, 판매 품목, 출력 데이터

auction
  → 경매 lot, 경매 시도, 결과 행, 반환 확인, 정산

payment
  → 입금 확인, 부분입금, 거래처 잔액, 입금 이벤트

print
  → A5 전표 출력 데이터
```

MSA로 나누지 않은 이유는 명확했다.

첫째, 아직 팀 규모가 작고 운영 복잡도를 늘릴 이유가 없었다.
둘째, 도메인들이 서로 강하게 연결되어 있었다.
셋째, 베타 버전에서는 빠르게 구현하고 실제 운영 피드백을 받는 것이 더 중요했다.

예를 들어 판매 전표를 출고 완료로 바꾸면 난 묶음 수량이 바뀌고, 입금 상태도 연결된다.
경매 정산은 경매 lot과 거래처, 입금 이벤트에 연결된다.

이런 상황에서 서비스를 너무 일찍 분리하면 네트워크 호출, 데이터 정합성, 배포 단위가 모두 복잡해진다.

그래서 우선은 하나의 애플리케이션으로 두되, 코드 내부의 모듈 경계를 지키는 방향을 선택했다.

## 계층 구조

백엔드는 기본적으로 다음 계층으로 나누었다.

```text id="oxip0m"
controller
service/application
domain/entity
repository
dto
```

각 계층의 역할은 최대한 단순하게 가져가려고 했다.

```text id="ty베타 버전r9"
Controller
  → 요청과 응답 처리

Service
  → 유스케이스와 트랜잭션 처리

Entity
  → DB 매핑과 최소 도메인 규칙

Repository
  → 데이터 접근

DTO
  → 외부 입출력 구조
```

Controller에는 비즈니스 로직을 넣지 않으려고 했다.
요청을 받고, DTO를 검증하고, Service를 호출한 뒤 응답을 반환하는 정도로 제한했다.

핵심 로직은 Service에서 처리했다.
특히 판매, 경매, 입금처럼 여러 엔티티가 함께 바뀌는 기능은 트랜잭션 경계를 명확히 잡는 것이 중요했다.

## 데이터베이스: PostgreSQL과 Flyway

운영 데이터는 PostgreSQL에 저장했다.

처음에는 SQLite로 시작할 수도 있었지만, 판매, 정산, 입금처럼 데이터 정합성이 중요한 기능이 많았다.
그리고 운영 배포까지 고려하면 처음부터 PostgreSQL을 사용하는 편이 낫다고 판단했다.

DB 변경 관리는 Flyway로 했다.

농장 관리 시스템은 개발 중에도 테이블이 계속 바뀌었다.

```text id="kw6yu9"
난 묶음에 품종 연결 추가
입고 기록 추가
경매 lot 상태 추가
입금 이벤트 추가
배드 세그먼트 추가
```

이런 변경을 수동 SQL로만 관리하면 운영 배포 때 실수하기 쉽다.
그래서 마이그레이션 파일로 변경 이력을 남기는 방향으로 잡았다.

## OpenAPI 문서화

API는 OpenAPI를 기준으로 관리했다.

```text id="nsoqfc"
docs/api/openapi.yaml
docs/api/slices/*.openapi.yaml
```

기능이 많아질수록 프론트엔드와 백엔드 사이의 요청/응답 구조를 맞추는 것이 중요해졌다.

예를 들어 판매 전표 생성, 경매 결과 입력, 입고 등록 같은 API는 요청 필드가 많다.
문서 없이 기억에 의존하면 프론트엔드와 백엔드가 쉽게 어긋난다.

그래서 API 상세 명세는 OpenAPI를 기준으로 두고, 일반 문서에는 도메인 규칙과 화면 흐름을 중심으로 정리했다.

## 삭제보다 이력 보존

이 프로젝트에서 중요하게 잡은 원칙 중 하나는 삭제보다 이력 보존이었다.

농장 운영 데이터는 나중에 다시 확인해야 하는 경우가 많다.
특히 다음 데이터는 단순 삭제하면 위험하다.

```text id="t19nm7"
작업 이력
위치 이동 이력
판매 전표
경매 lot 상태 이력
입금 이벤트
원본 가져오기 데이터
```

예를 들어 경매 lot 상태가 잘못 입력되었다고 해서 기존 기록을 바로 지우면, 나중에 어떤 판단을 했는지 알 수 없다.
입금 이벤트도 마찬가지다. 잘못 입력했더라도 삭제보다 취소나 보정 이벤트를 남기는 편이 안전하다.

그래서 베타 버전에서는 운영 데이터는 가능하면 상태 변경이나 보정 이력으로 처리하는 방향을 잡았다.

물론 모든 데이터를 무조건 보존하는 것은 아니다.
입고 취소처럼 명백한 오입력이고 후속 데이터가 없는 경우에는 삭제할 수 있어야 한다.
하지만 기본 방향은 "운영 흐름이 남아야 하는 데이터는 삭제하지 않는다"였다.

## 배포를 고려한 구조

베타 버전은 로컬에서만 돌아가는 프로젝트가 아니라 실제 배포를 목표로 했다.

운영 후보는 여러 가지가 있었다.

```text id="2fa7wk"
농장 내부 미니 PC
개인 서버
소형 클라우드 VM
```

최종적으로는 내가 직접 구축한 서버 환경 위에 올리는 방향으로 진행했다.
프론트엔드와 백엔드를 컨테이너 이미지로 만들고, PostgreSQL과 함께 운영할 수 있도록 구성했다.

초기 운영에서 중요하게 본 것은 화려한 인프라보다 안정성이었다.

```text id="t48wfs"
환경 변수 분리
DB 마이그레이션 확인
서버 재시작 후 데이터 유지 확인
헬스체크
백업
```

특히 백업은 반드시 필요했다.
운영 데이터가 쌓인 이후에는 DB가 프로젝트 그 자체가 되기 때문이다.

## 정리

Green-house 베타 버전의 기술 구조는 대단히 특별한 기술을 쓰는 방향은 아니었다.

오히려 익숙하고 검증된 기술을 조합해서, 실제 운영까지 가져갈 수 있는 구조를 만드는 것에 집중했다.

```text id="8vuwp4"
Frontend
  → Next.js / TypeScript / Tailwind CSS

Backend
  → Spring Boot / Java 21 / JPA

Database
  → PostgreSQL / Flyway

Architecture
  → 모듈러 모놀리스

  → OpenAPI / Markdown 문서
```

이번 프로젝트에서 중요했던 것은 기술 자체보다 기술을 선택한 이유였다.
