난 묶음 관리 화면을 처음 만들었을 때는 기능을 구현하는 것만으로도 충분했다.

농장의 동과 다이를 가로로 넘겨 보고, 배치된 난 묶음을 선택하면 작업 이력을 확인할 수 있었다. 데이터가 적을 때는 이 구조가 특별한 문제 없이 동작했다.

실제 농장 데이터에서는 화면을 넘기거나 작업 이력을 확인할 때 반응이 조금 늦다고 느껴지는 정도였다. 사용하지 못할 만큼 오래 멈추지는 않았지만, 데이터가 늘어나면 현재 구조가 더 큰 문제가 될 가능성이 있었다.

원인을 분명하게 확인하기 위해 모든 배치 칸을 난 묶음으로 채운 고밀도 데이터를 만들었다. 이 조건에서는 화면에 보이는 다이가 세 개뿐인데도 2,216개의 난 묶음이 모두 DOM에 올라갔고, 캐러셀을 이동할 때 작업 이력 요청도 대량으로 발생했다. 병목을 드러내기 위한 연속 이동 시나리오에서는 동작이 끝날 때까지 약 26초가 걸렸다.

이번 개선에서는 특정 최적화 기법 하나를 적용하기보다 화면에 필요한 컴포넌트와 데이터의 범위를 함께 줄였다.

* 화면 주변의 다이만 무거운 콘텐츠를 마운트한다.
* 캐러셀 이동과 작업 이력 조회 대상 선택을 분리한다.
* 난 묶음별 이력 요청을 선택 범위 기준의 페이지 요청으로 바꾼다.
* 이미 조회했거나 조회 중인 요청을 다시 만들지 않는다.
* 더 이상 필요하지 않은 요청은 취소한다.

## 고밀도 데이터에서 드러난 문제

실제 환경에서 느껴지던 작은 지연의 원인을 확인하고 개선 전후를 비교하기 위해 다음과 같은 고정 데이터를 구성했다. 농장의 일반적인 배치 상태를 그대로 재현한 것이 아니라, 모든 배치 칸에 난 묶음을 넣어 병목을 확대하는 성능 측정용 데이터다.

* 동 15개
* 물리 다이 45개
* 논리 구역 90개
* 배치 칸 1,108개
* 난 묶음 2,216개
* 난 묶음별 통합 작업 이력 100건

난 묶음 관리 화면은 이 데이터를 하나의 연속된 맵으로 보여준다. 사용자는 한 화면에서 세 개의 다이를 확인하고, 좌우로 이동하며 다른 다이를 살펴본다.

문제는 보이는 범위와 실제로 처리하는 범위가 다르다는 점이었다.

화면에는 세 개의 다이만 보였지만 기존 구현은 캐러셀에 포함된 45개 다이의 내부 콘텐츠를 모두 렌더링했다. 그 결과 다이의 구역과 눈금뿐 아니라 2,216개의 난 묶음 노드가 처음부터 DOM에 마운트됐다.

작업 이력 조회도 비슷했다. 동이나 다이를 선택하면 해당 범위에 속한 난 묶음 ID를 프론트엔드에서 모두 수집한 뒤, 난 묶음마다 이력 API를 따로 호출했다.

```text
동 선택
 ├─ 난 묶음 1의 작업 이력 요청
 ├─ 난 묶음 2의 작업 이력 요청
 ├─ 난 묶음 3의 작업 이력 요청
 └─ ...
```

동 이력을 한 번 표시할 때 요청은 중앙값 기준 156회 발생했다. 응답 데이터는 약 8.28MiB였고, 화면에 이력이 표시되기까지 약 2.1초가 걸렸다.

UI에서 필요한 것은 최근 작업 일부였지만, 프론트엔드는 범위에 포함된 난 묶음의 이력을 각각 받아 합치고 다시 정렬하고 있었다.

### 화면 이동이 이력 요청까지 다시 만들던 구조

캐러셀을 움직이는 것은 화면에서 다른 위치를 보기 위한 동작이다. 하지만 기존에는 캐러셀의 현재 위치가 바뀌면 작업 이력의 선택 범위도 함께 바뀌었다.

사용자가 다이를 연속해서 이동하는 동안 곧 사용하지 않을 이력 요청이 계속 만들어졌다. 모든 칸을 채운 상태에서 10번 연속으로 스와이프하는 부하 시나리오에서는 한 번의 실행에 이력 API가 3,182회 호출됐고, 그중 2,496회는 중복 요청이었다. 내려받은 응답은 약 169.71MiB에 달했다.

렌더링과 네트워크 문제가 따로 존재한 것이 아니었다. 캐러셀 이동으로 넓은 컴포넌트 트리가 다시 렌더링되고, 같은 상태 변경이 새로운 이력 요청까지 만드는 구조였다.

## 같은 조건을 반복하기 위한 성능 E2E

체감만으로 최적화 효과를 판단하면 실행할 때마다 결과가 달라질 수 있다. 먼저 개선 전후를 같은 조건에서 비교할 수 있도록 Playwright 기반 성능 E2E를 만들었다.

측정은 Next.js production build와 실제 Spring Boot 애플리케이션, 별도의 PostgreSQL E2E 데이터베이스를 사용했다. 브라우저와 화면 크기, 데이터도 고정했다.

* Playwright Chromium
* 브라우저 화면 영역(viewport) 1180×820
* worker 1개
* 시나리오별 워밍업 1회
* 시나리오별 본측정 5회
* 고정 seed 데이터

각 시나리오에서는 사용자 동작부터 렌더링이 끝날 때까지의 시간뿐 아니라 API 요청 수와 payload, 마운트된 다이 수, 난 묶음 DOM 노드 수와 중복 요청 수도 함께 기록했다.

렌더 완료 시점은 관련 네트워크 응답이 끝난 뒤 두 번의 animation frame이 지난 시점으로 정했다. 속도를 줄이는 과정에서 데이터가 누락되지 않았는지 확인하기 위해 선택 범위와 표시된 이력의 일치 여부, 최신 작업 표시, 드래그 이후 선택 유지, 콘솔 오류와 실패 요청도 함께 검사했다.

## 화면 주변만 마운트

가장 먼저 화면 밖의 렌더링 범위를 줄였다.

캐러셀은 이동 거리와 각 슬라이드의 위치를 계산하기 위해 전체 슬라이드의 외곽 구조가 필요하다. 그렇다고 화면에서 멀리 떨어진 슬라이드의 구역, 눈금과 난 묶음까지 모두 마운트할 필요는 없었다.

따라서 45개 슬라이드의 크기와 위치는 그대로 유지하고, 내부의 무거운 콘텐츠만 현재 화면 주변에 마운트했다.

```text
이전
45개 슬라이드
 └─ 모든 다이와 난 묶음 마운트

개선 후
45개 슬라이드의 외곽 구조 유지
 ├─ 앞쪽 한 화면: 내부 콘텐츠 마운트
 ├─ 현재 화면: 내부 콘텐츠 마운트
 ├─ 뒤쪽 한 화면: 내부 콘텐츠 마운트
 └─ 나머지 슬라이드: 크기만 유지
```

한 화면에 다이 세 개가 보이는 측정 조건에서는 최대 아홉 개의 다이만 무거운 콘텐츠를 가진다. 나머지는 높이와 폭만 유지하는 빈 컨테이너로 남는다.

이 방식으로 캐러셀의 위치 계산과 연속 이동 방식은 유지하면서 마운트된 다이는 45개에서 9개로, 난 묶음 DOM 노드는 2,216개에서 288개로 줄었다. 다이는 80%, 난 묶음 노드는 약 87% 감소했다.

연속 이동을 마친 뒤에도 DOM 노드가 계속 쌓이지 않는지 확인했고, 개선 전후 모두 증가량은 0이었다. 필요한 범위가 바뀔 때 기존 콘텐츠를 해제하고 새 범위를 마운트하는 구조가 유지된 것이다.

## 난 묶음별 요청을 선택 범위 요청으로 변경

렌더링 범위를 줄이는 것만으로는 수백 번씩 발생하는 작업 이력 요청을 해결할 수 없었다. 이력 조회의 단위를 난 묶음에서 사용자가 선택한 범위로 바꿨다.

프론트엔드가 난 묶음 ID를 모두 모아 각각 요청하는 대신 동, 물리 다이, 논리 구역 또는 난 묶음의 ID를 API에 직접 전달한다.

```text
GET /work-history
  ?scopeType=HOUSE
  &scopeId=8
  &page=0
  &size=20
```

백엔드는 선택한 범위에 포함되는 난 묶음을 찾고, 작업 이력을 날짜와 ID 기준으로 정렬해 페이지 단위로 반환한다. 여러 응답을 합치고 정렬하던 책임도 프론트엔드에서 제거했다.

선택 정보 영역에는 최근 작업만 필요하므로 처음 20건만 가져온다. 난 묶음의 상세 이력은 사용자가 상세 창을 열었을 때 10건 단위로 불러오도록 분리했다.

```text
선택 정보
 └─ 최근 작업 20건

난 묶음 상세 이력
 ├─ 첫 페이지 10건
 ├─ 다음 페이지 10건
 └─ ...
```

상세 창을 열지 않으면 나머지 이력은 다운로드하지 않는다. UI가 지금 보여줄 수 있는 범위와 API가 반환하는 데이터의 범위를 맞춘 것이다.

## 이동과 선택을 서로 다른 상태로 분리

다이를 넘겨 보는 동작과 작업 이력의 범위를 선택하는 동작은 겉으로는 같은 맵 안에서 일어나지만 목적이 다르다.

캐러셀 이동은 농장의 다른 위치를 보기 위한 탐색이고, 동이나 다이 또는 난 묶음 선택은 해당 대상의 정보를 보기 위한 동작이다. 두 상태를 분리해 캐러셀을 이동해도 사용자가 명시적으로 선택한 이력 범위가 유지되도록 변경했다.

이후 단순한 다이 이동에서는 작업 이력 API를 호출하지 않는다. 개선 전 연속 스와이프 한 번에 3,182회 발생하던 이력 요청과 2,496회의 중복 요청이 모두 0회가 됐다.

선택 상태가 이동 중에도 유지되는지는 자동화 테스트로 함께 확인했다. 요청을 없애기 위해 선택을 초기화하거나 화면에 잘못된 이력을 남기는 방식이 되지 않도록 했다.

## 같은 요청은 다시 만들지 않기

범위 기반 API로 요청 수를 줄인 뒤에는 남은 요청의 생명주기를 정리했다.

조회 결과는 선택 유형과 ID를 조합한 키로 메모리 캐시에 저장했다.

```text
HOUSE:8
PHYSICAL_BED:22
BED_ZONE:47
ORCHID_GROUP:1069
```

같은 범위를 다시 선택하면 네트워크 요청 없이 캐시된 결과를 사용한다. 상세 이력은 난 묶음 ID와 페이지, 페이지 크기를 조합한 별도의 키로 관리했다.

동일한 키의 요청이 이미 진행 중일 때는 새 요청을 만들지 않고 진행 중인 비동기 작업인 Promise를 공유했다. React의 `useEffect`가 다시 실행되거나 짧은 시간 안에 같은 대상을 다시 선택해도 하나의 요청과 응답을 함께 사용한다.

반대로 사용자가 다른 대상을 선택해 이전 응답이 필요 없어지면 브라우저의 요청 취소 기능인 `AbortController`로 진행 중인 요청을 중단했다. 컴포넌트가 화면에서 제거될 때도 남아 있는 요약과 상세 요청을 정리했다. 이를 통해 불필요한 네트워크 사용뿐 아니라 이전 선택의 응답이 뒤늦게 도착하는 경쟁 상황도 줄였다.

캐시가 오래된 데이터를 보여주지 않도록 작업 등록이나 데이터 변경이 성공하면 캐시를 비우고 현재 선택 범위를 다시 조회했다.

## 변경되지 않은 난 묶음은 다시 렌더링하지 않기

렌더링 대상 자체를 줄인 뒤에는 남아 있는 난 묶음 컴포넌트의 불필요한 렌더링을 줄였다.

React에서는 부모 컴포넌트의 상태가 바뀌어 다시 렌더링되면 그 아래의 자식 컴포넌트도 기본적으로 다시 렌더링된다. 자식이 같은 난 묶음을 보여주고 있더라도 부모가 전달하는 값인 prop을 다시 확인하는 과정이 발생한다.

`React.memo`는 이때 자식에게 전달된 prop이 이전과 같으면 해당 컴포넌트의 렌더링을 건너뛰게 한다. 난 묶음 하나를 표시하는 `OrchidGroupBlock`처럼 같은 형태의 컴포넌트가 많이 반복되는 화면에서는 부모의 다른 상태가 바뀔 때 모든 난 묶음을 다시 처리하는 일을 줄일 수 있다.

다만 `React.memo`는 prop을 비교할 때 객체와 함수의 내용이 아니라 참조가 같은지를 확인한다. 기존에는 각 난 묶음에 선택 함수를 전달할 때 다음과 같이 화살표 함수를 바로 만들었다.

```tsx
onSelect={() => onSelectOrchidGroup(orchidGroup.id)}
```

이 함수는 동작이 같아도 부모가 렌더링될 때마다 새로 생성된다. `React.memo`의 입장에서는 `onSelect` prop이 매번 다른 함수로 바뀐 것이므로 렌더링을 건너뛸 수 없다.

`useCallback`은 컴포넌트가 다시 렌더링돼도 의존하는 값이 바뀌지 않았다면 이전에 만든 함수의 참조를 유지하는 React Hook이다. 함수의 실행 자체를 빠르게 만드는 기능은 아니며, 같은 함수를 prop으로 계속 전달해야 할 때 불필요한 변경으로 인식되지 않게 하는 역할을 한다.

공통 선택 함수를 `useCallback`으로 유지하고, 선택할 난 묶음 ID는 별도의 prop으로 전달하도록 구조를 바꿨다.

```tsx
onSelect={onSelectOrchidGroup}
orchidGroupId={orchidGroup.id}
```

이제 부모가 다시 렌더링돼도 선택 함수의 참조는 그대로 유지된다. 여기에 `React.memo`를 적용하면 난 묶음 데이터, ID, 선택 여부와 표시 속성이 모두 같은 블록은 렌더링을 건너뛸 수 있다.

정리하면 `useCallback`은 자식에게 전달하는 함수가 불필요하게 바뀌지 않도록 하고, `React.memo`는 전달된 값이 바뀌지 않은 자식의 렌더링을 생략한다. 두 기능을 함께 사용해야 이 화면에서 의도한 효과를 얻을 수 있었다. 모든 컴포넌트에 무조건 적용한 것은 아니며, 같은 난 묶음 블록이 수백 개 반복되는 구간에만 사용했다.

다만 아래 성능 수치는 이 마지막 메모이제이션 변경보다 먼저 수집됐다. 따라서 측정 결과를 `React.memo`의 효과로 해석하지 않고, 화면 부분 마운트와 작업 이력 조회 구조를 개선한 결과로 본다.

## 성능 측정 결과

개선 전후 모두 모든 배치 칸을 채운 같은 데이터와 브라우저 조건에서 각 시나리오를 한 번 워밍업한 뒤 다섯 번 측정했다. 표의 시간은 다섯 번의 중앙값이다. 실제 농장의 일반적인 사용 시간을 나타내는 수치가 아니라, 병목을 크게 만든 조건에서 구조 변경의 효과를 비교한 결과다.

| 시나리오 | 개선 전 | 개선 후 | 단축률 |
|---|---:|---:|---:|
| 동 이력 표시 | 2,099ms | 727.9ms | 65.3% |
| 다음 다이 Cold 이동 | 1,514.4ms | 448.5ms | 70.4% |
| 이전 다이 Cold 이동 | 1,610.3ms | 423.6ms | 73.7% |
| 다이 Warm 재방문 | 1,534.4ms | 423.5ms | 72.4% |
| 연속 스와이프 | 25,997.7ms | 6,850.3ms | 73.7% |
| 다이 이력 표시 | 1,183.6ms | 277.8ms | 76.5% |
| 난 묶음 이력 표시 | 933.5ms | 237ms | 74.6% |

고밀도 측정 조건에서 주요 동작의 중앙 응답 시간은 65~77% 줄었다. 가장 큰 부하를 준 연속 스와이프 시나리오는 약 26초에서 6.85초로 단축됐다. 실제 환경에서 매번 26초를 기다렸다는 의미는 아니며, 평소 조금 느리게 느껴지던 원인이 데이터 밀도가 높을수록 빠르게 커지는 구조였다는 것을 보여주는 수치다.

요청 수와 데이터 크기의 변화는 더 컸다.

| 항목 | 개선 전 | 개선 후 |
|---|---:|---:|
| 마운트된 다이 | 45개 | 9개 |
| 난 묶음 DOM 노드 | 2,216개 | 288개 |
| 연속 이동 중 이력 요청 | 3,182회 | 0회 |
| 연속 이동 중 중복 이력 요청 | 2,496회 | 0회 |
| 동 이력 1회 payload 중앙값 | 약 8.28MiB | 약 11.11KiB |

동 이력은 난 묶음마다 요청하는 대신 선택한 동을 기준으로 한 번만 조회하게 됐다. 다이와 난 묶음 이력은 첫 조회 결과를 캐시하므로 반복 측정에서는 추가 요청이 발생하지 않았다.

개선 후에는 화면 이동과 이력 선택을 분리했기 때문에 단순 이동에서 이력 데이터를 내려받지 않는다.

성능을 줄이는 과정에서 선택 범위와 이력의 일치 여부, 최신 작업 표시와 드래그 이후 선택 상태는 모두 테스트를 통과했다. 콘솔 오류와 실패한 요청도 발생하지 않았다.

각 시나리오의 본측정이 다섯 번이므로 p95는 사실상 가장 느린 표본에 가깝다. 그래서 대표 결과에는 중앙값을 사용했다. 또한 측정 시간에는 프론트엔드 렌더링뿐 아니라 API 요청과 서버 응답도 포함된다. 이번 결과는 React 렌더링만의 개선이 아니라 프론트엔드의 렌더링 범위와 서버의 작업 이력 조회 흐름을 함께 바꾼 결과다.

## 필요한 범위를 먼저 줄이기

처음에는 많은 난 묶음 컴포넌트가 있으니 `React.memo`부터 적용하면 될 것처럼 보였다. 하지만 실제 병목은 변경된 컴포넌트를 다시 그리는 문제보다 화면 밖의 컴포넌트까지 처음부터 마운트하고, 한 번의 이동이 수천 건의 요청으로 확장되는 구조에 가까웠다.

이번 개선에서는 다음 순서로 처리 범위를 줄였다.

* 화면 밖의 무거운 콘텐츠를 마운트하지 않는다.
* 선택 범위에 필요한 최근 이력만 한 번에 조회한다.
* 화면 탐색이 데이터 조회를 다시 실행하지 않도록 상태를 분리한다.
* 이미 조회했거나 조회 중인 데이터는 함께 사용한다.
* 더 이상 필요하지 않은 비동기 작업은 중단한다.
* 남은 컴포넌트 중 변경되지 않은 항목의 렌더링을 건너뛴다.

하나의 최적화 기법보다 사용자가 지금 보고 있는 화면과 필요로 하는 데이터가 어디까지인지 정하는 일이 더 큰 효과를 만들었다.

성능 문제를 확인할 때도 재렌더링 횟수만 보기보다 한 번의 사용자 동작이 어디까지 영향을 주는지 함께 살펴봐야 한다. 화면 밖의 컴포넌트가 마운트되어 있는지, UI에 표시하지 않을 데이터까지 받고 있는지, 탐색과 선택처럼 의미가 다른 상태가 하나로 묶여 있는지에 따라 처리량이 크게 달라질 수 있다.

이번 개선으로 실제 환경에서 느껴지던 반응 지연을 줄이고, 모든 배치 칸을 채운 조건에서도 다이 이동과 작업 이력 조회가 이전보다 안정적으로 동작하게 됐다.
